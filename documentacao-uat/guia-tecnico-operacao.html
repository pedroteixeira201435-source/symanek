1. Visão geral da arquitetura

  • Site público — aplicação Next.js 14, alojada na Vercel (root directory site-publico).
  • Suite de gestão — aplicação Vite + React, alojada na Vercel (build vite build → dist).
  • Backend — Supabase (PostgreSQL gerido).
  • Auth — Supabase Auth (email/password), perfis em public.profiles.
  • Base de dados — Postgres com tabelas de domínio (students, staff, programmes, courses, applications, invoices, payments, results, …).
  • Storage — buckets Supabase para documentos e comprovantes (cartas, EFT).
  • RPCs SECURITY DEFINER — escritas sensíveis passam por funções controladas (não DML direto).
  • RLS — Row Level Security ativa nas tabelas sensíveis; cada utilizador só vê o que lhe é permitido.

4. Como criar acessos reais no Supabase

  1. Criar o utilizador em Supabase Auth (Authentication → Users → Add user) com [email do admin].
  2. Confirmar o email (ou marcar como email confirmed).
  3. Criar/atualizar o registo correspondente em public.profiles.
  4. Definir role (papel funcional) e suite_role (papel na Suite).
  5. Para estudante, vincular students.user_id ao auth.users.id (ver secção 5).
  6. Obrigar troca da password inicial, ou definir um processo manual documentado para entregar a [password temporária] de forma segura.

5. Como dar acesso a um estudante

  1. O estudante tem de existir em public.students.
  2. Tem de existir um auth user associado (Supabase Auth) com [email do estudante].
  3. students.user_id tem de apontar para auth.users.id do mesmo utilizador.
  4. O portal só deve mostrar dados do próprio estudante (garantido por RLS — validar).
  5. Testar o login depois de configurado (ver PDF de UAT, secção I — Student Portal).
Verificar estudantes sem conta ligada com a query da secção 16 (students.user_id IS NULL).

7. Capacidades dos cursos

  • capacity = 0 força lista de espera (waitlist) — matrículas legítimas caem em espera indevidamente.
  • Antes de qualquer matrícula real, preencher a capacidade real de cada curso.
  • Validar enrolled face à capacidade.
  • Usar o template/importador do projeto:
    • Template: supabase/templates/course-capacities.csv
    • Aplicar: APPLY_COURSE_CAPACITIES=1 npm run apply:course-capacities

8. Segurança / RLS / RPC

  • Tabelas sensíveis devem ser RPC-only (sem DML direto pelo cliente).
  • Raw DML bloqueado em: students, staff, payments.
  • Todas as escritas passam por RPCs SECURITY DEFINER:
RPCAção
approve_applicationAprovar candidatura
reject_applicationRejeitar candidatura
mark_paidMarcar como pago
student_upsertCriar/atualizar estudante
student_archiveArquivar estudante
hold_placeReservar vaga
hold_clearLibertar reserva
staff_upsertCriar/atualizar staff
pay_invoicePagar fatura
confirm_invoice_paymentConfirmar pagamento de fatura

Confirmar via queries da secção 16 que authenticated/anon não têm INSERT/UPDATE/DELETE direto nas tabelas sensíveis.

10. CI/CD

  • Workflow do GitHub Actions deve estar ativo (.github/workflows/ci.yml).
  • Build da Suite deve passar (npm run build).
  • Build do site público deve passar (cd site-publico && npm run build).
  • Validação de RLS/RPC deve ser bloqueante (falha vermelha bloqueia merge).
  • continue-on-error não deve existir nos jobs críticos.
  • Fazer push de .github/workflows/ci.yml exige um GitHub PAT com scope workflow.

11. Deploy na Vercel

  • Site público: root directory site-publico (framework Next.js).
  • Suite: root da app Vite (build npm run build → dist, conforme vercel.json).
  • Confirmar as variáveis de ambiente (secção 3) antes do deploy.
  • Validar endpoints após o deploy (site abre, Suite faz login, dados reais aparecem).
  • Cuidado com deploy cruzado — não apontar o projeto do site para o root da Suite (ou vice-versa).

16. Anexo — SQL / verificações úteis

Executar no SQL Editor do Supabase. Nenhuma query contém segredos.

Políticas RLS nas tabelas sensíveis

select tablename, policyname, cmd
from pg_policies
where tablename in ('students','staff','payments');

Grants diretos a authenticated / anon (devem ser mínimos)

select table_name, grantee, privilege_type
from information_schema.role_table_grants
where table_schema='public'
  and table_name in ('students','staff','payments')
  and grantee in ('authenticated','anon');

Contagem de estudantes

select count(*) from public.students;

Cursos com capacidade 0 (causam waitlist)

select code, title, capacity, enrolled
from public.courses
where coalesce(capacity, 0) = 0;

Perfis sem suite_role

select id, full_name, email, suite_role
from public.profiles
where suite_role is null;

Estudantes sem conta de utilizador ligada

select id, reference, full_name, email
from public.students
where user_id is null;

Candidaturas por estágio

select stage, count(*)
from public.applications
group by stage
order by count(*) desc;

Rasto de auditoria recente

select created_at, actor, action, entity, entity_id
from public.audit_log
order by created_at desc
limit 50;
